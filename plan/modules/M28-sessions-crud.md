## Objective
Sessions become first-class rows: create/edit/delete via dialog, browse in a searchable/filterable List view, hold unscheduled ones in a Drafts tray, and promote an accepted abstract into a linked session in one click. This is also where `moveSession` — the version-CAS mutation everything else (drag, ICS, public schedule) hangs off — gets built. When done: an organizer can add a session by hand, or promote a seeded accepted submission, see it in the tray or list, edit it, and publish it, all without drag-and-drop existing yet.

## Step-by-step implementation

1. **Contract-first slice.** Create `index.ts`/`index.client.ts` exporting the full signatures above as typed stubs (`saveSession` etc. throwing `not implemented` or returning fixture data), plus `AgendaViewProps`. Create the 5 placeholder view components (`day-view.tsx`, `week-view.tsx`, `track-view.tsx`, `room-view.tsx`, `conflicts-view.tsx`) as one-liners: `export default function DayView(props: AgendaViewProps) { return <EmptyState title="Day view" hint="Coming Monday" />; }` (swap the copy per view). Create `agenda-page.tsx` importing all 6 view components (list + 5 placeholders) **statically by exact file path** — this is the only file that imports every view; M30 and M31 never need to touch it, they only ever edit the *contents* of their own placeholder file. **Also in Step 1 (Sat AM): `scripts/seed/agenda.ts`** — WS-E's seed module ([M09](./M09-seed-demo-script.md) §3). Nothing else in the build can write it, and four surfaces render against it: **~15 sessions** across the event days, mostly `published`, **3 unscheduled** (NULL times → the tray), **the two named conflicting pairs `⚠ Demo conflict A` / `⚠ Demo conflict B`** (one room clash, one speaker clash — [M29](./M29-conflict-engine.md)'s AC asserts these two by name), and at least one **back-to-back** pair that must **not** be flagged. Session times authored via `zonedInputToUtc(local, 'America/Los_Angeles')`, never bare UTC literals. Deterministic `seedId` ids, idempotent `ON CONFLICT (id) DO UPDATE`; register with the architect-owned orchestrator after `submissions`. This is also what [M32](./M32-public-schedule-gallery.md)'s Sunday public pages and [M35](./M35-ics-calendar-invites.md)'s lifecycle test read.
**Done when:** `agenda-page.tsx` compiles and renders a tab bar that switches between empty-state placeholders and a (stub) list view; route `src/app/(admin)/events/[eventId]/agenda/page.tsx` reads `searchParams.view`/`searchParams.day`, calls `listSessions`+`getSchedulableSessions`+`detectConflicts` server-side, and renders `<AgendaPage .../>` with hydrated props; and `pnpm seed && pnpm seed` leaves exactly 15 sessions with both named conflict pairs present.

2. **`server/queries.ts`.** `listSessions(eventId, filters)`: Drizzle select joining `rooms`/`tracks`/`session_formats`/`session_speakers`+`contacts` (speaker name only — no bio/headshot needed here), event-scoped (`WHERE event_id = $eventId`, composite FK makes cross-event joins impossible by construction), optional filters by `search` (ILIKE on title), `trackId`, `roomId`, `status`, `day` (compare `starts_at` converted to event tz date-key — **do not** `DATE(starts_at)` in raw UTC; either filter client-side using `eventDayKey` from `time.ts` on the full unfiltered-by-day result, or pass the day's `[startOfDayUtc, endOfDayUtc)` bounds computed via `time.ts` into the query). Return NULL-time rows too (List view/tray needs them) sorted `starts_at NULLS LAST, title`. `getSchedulableSessions(eventId, day?)`: same base query, map every row through M29's `toScheduledSession`, filter out `null`s (excludes NULL-time rows structurally — this is the "normalize at the edge" step quality-strategy calls for). `getMySessions(eventId, contactId)`: join `session_speakers WHERE contact_id = $contactId` → `sessions WHERE event_id = $eventId AND starts_at IS NOT NULL` (IDOR-safe: contactId is a required arg, never inferred). **Done when:** each function returns correct rows against seeded fixture data; a query with a mismatched `contactId` returns `[]`.

3. **`server/mutations.ts` — `saveSession` (create/update, single-statement, no withTx).** Zod-validate input: `title` (1–255), `descriptionHtml` (pass through `sanitize()` before write — resolution #2, never store raw HTML), `formatId`/`trackId`/`roomId` nullable, `startsAt`/`endsAt` both-null-or-both-set with `endsAt > startsAt` (mirrors the DB CHECK — backstop, not a replacement), `speakerContactIds: ContactId[]` deduped via `Set` before write (session_speakers PK is `(session_id, contact_id)` — a duplicate in the array must not hit the DB twice), `status: 'draft'|'published'`. **Create**: generate a slug via `slug.ts` (slugify title + numeric suffix retry loop on `UNIQUE(event_id, slug)` violation — catch the constraint error, don't pre-check), insert `sessions` row, then insert `session_speakers` rows (one statement per row is fine; low cardinality). **Update**: guarded `UPDATE sessions SET …, row_version = row_version + 1, updated_at = now() WHERE id = $id AND event_id = $eventId AND row_version = $expectedVersion RETURNING *`; 0 rows → throw `STALE_WRITE` (409). **Publish path — the `schedule_revision` bump is NOT optional here.** `saveSession`'s guarded UPDATE bumps on the **post-update** state — a `CASE` reads the pre-update row, so the condition must use the incoming `$newStatus` parameter and count the draft→published transition explicitly (a draft published with times set must enqueue `schedule_assigned`; testing only the old `status` column would silently skip it):
```sql
schedule_revision = schedule_revision + CASE
  WHEN $newStatus = 'published'
   AND (status IS DISTINCT FROM 'published'   -- draft→published: the schedule just became real for speakers
        OR starts_at IS DISTINCT FROM $newStarts OR ends_at IS DISTINCT FROM $newEnds OR room_id IS DISTINCT FROM $newRoom)
  THEN 1 ELSE 0 END
```
(`moveSession`'s simpler `WHEN status = 'published'` form stays correct there because `moveSession` never changes `status` — old and new are the same row value.)
and **only then** calls the shared non-transactional helper **`notifySchedule(db, eventId, sessionId, priorRow, newRow)`** (renamed from `bumpScheduleAndNotify` so the name stops implying it does the bump — it does not; it only enqueues). Why this is load-bearing: the `sched` idempotency recipe is `{eventId}:sched:{sessionId}:{contactId}:{schedule_revision}`. If a dialog-driven time change enqueued **without** bumping `schedule_revision`, the key would equal the previous send's key and `enqueueEmail`'s `ON CONFLICT DO NOTHING` would silently swallow the email — and [M35](./M35-ics-calendar-invites.md)'s SEQUENCE monotonicity, which is derived from `schedule_revision`, would stall too.
**The session row and its `session_speakers` set change atomically even without `withTx`:** the update runs as **one data-modifying CTE statement** — `WITH updated AS (UPDATE sessions … RETURNING *), del AS (DELETE FROM session_speakers WHERE session_id = (SELECT id FROM updated)), ins AS (INSERT INTO session_speakers … SELECT … FROM updated, unnest($speakers)) SELECT * FROM updated` — so a crash can never leave the session updated with the old speaker set (a multi-statement delete-then-insert could). Only the email enqueue stays outside.
`notifySchedule` is a **best-effort, non-atomic** follow-up: after that statement returns successfully, run one more single statement inserting `communication_logs` rows (via `enqueueEmail`), then `nudgeOutbox(ctx.waitUntil)` from `@/features/comms` (best-effort, failures swallowed). **Recipients come from the explicit before/after speaker sets already in hand** — `priorRow`'s speaker list (read for the guard) and the validated input set — never from a fresh `session_speakers` re-read that could race a concurrent edit: schedule notices go to the **after** set; speakers removed in this save get no schedule mail (their calendar CANCEL is [M35](./M35-ics-calendar-invites.md)'s diff against `calendar_invites`, not this path). A crash between the two statements loses only an email enqueue, never corrupts the schedule — acceptable and explicitly flagged, since `saveSession` is not one of the 8 audited `withTx` functions. **Done when:** create/update/delete round-trip in a PGlite test; stale `row_version` on update → 409; duplicate speaker ids in input collapse to one row; a simulated failure mid-save leaves session + speakers consistent (both old or both new); publishing a draft with times set enqueues `schedule_assigned` for each speaker in the input set.

4. **`moveSession` — the audited withTx function.** In `withTx(async tx => { … })`: `SELECT * FROM sessions WHERE id=$id AND event_id=$eventId FOR UPDATE`; not found → `NOT_FOUND`; `row.row_version !== input.version` → rollback, `STALE_WRITE`; else `UPDATE sessions SET starts_at=$, ends_at=$, room_id=$, row_version = row_version + 1, schedule_revision = schedule_revision + CASE WHEN status='published' AND (starts_at IS DISTINCT FROM $newStarts OR ends_at IS DISTINCT FROM $newEnds OR room_id IS DISTINCT FROM $newRoom) THEN 1 ELSE 0 END, updated_at = now() WHERE id=$id AND row_version=$version RETURNING *`. If the resulting row's `status = 'published'` and `schedule_revision` incremented: for each `session_speakers` row on this session, `enqueueEmail(tx, { eventId, templateKey: priorRow.startsAt === null ? 'schedule_assigned' : 'schedule_changed', contactId, idempotencyKey: idem.scheduled(eventId, id, contactId, newRow.schedule_revision), refs: { sessionId: id } })` — **import `idem` from `@/shared/contracts` and call the builder; never template the key inline** ([M02](./M02-shared-contracts.md) §8 owns the recipe, and M18's guardrail states the rule for the whole repo: "idempotency keys are contracts, not strings you invent"). After the transaction commits, fire the same best-effort post-commit nudge `saveSession` and the M16 submit path use — `nudgeOutbox(ctx.waitUntil)` from `@/features/comms` (failures swallowed; `enqueueEmail` stays inside the tx, the nudge only trims the cron-latency on delivery). Then compute the day's fresh conflict list via `getSchedulableSessions(eventId, dayOf(newRow.startsAt))` + `detectConflicts` **inside the same function, after the transaction commits** (read-only, doesn't need to be in the tx) and return it alongside the updated session DTO. **Done when:** PGlite test — two concurrent `moveSession` calls with the same stale `version` → exactly one succeeds, the other gets `STALE_WRITE`, `schedule_revision` untouched on the loser; moving a published session's time logs exactly one `communication_logs` row per speaker with the right idempotency key; moving a draft session enqueues nothing.

5. **`promoteSubmission(eventId, submissionId)`.** Idempotency check first: `SELECT id FROM sessions WHERE submission_id = $submissionId AND event_id = $eventId` — if found, return `{ sessionId: found.id }` unchanged (never duplicate on a double-click or re-promote). Otherwise, fetch the source row via `getAcceptedForScheduling`'s per-submission shape (call the WS-C export; the fixture stub returns the same 3 hardcoded rows regardless of `submissionId` during Sat/Sun — fine for building the UI, swap when M18 lands) and run **one CTE statement**: `WITH s AS (INSERT INTO sessions (event_id, submission_id, title, slug, description_html, track_id, format_id, starts_at, ends_at, status) VALUES (...) RETURNING id) INSERT INTO session_speakers (session_id, contact_id, role, sort_order) SELECT s.id, x.contact_id, CASE WHEN x.is_primary THEN 'speaker' ELSE 'co_speaker' END, x.sort_order FROM s, unnest($speakers) AS x(contact_id, is_primary, sort_order) RETURNING session_id` — single round trip, no withTx needed. New session is always `status = 'draft'` (organizer publishes explicitly). `starts_at`/`ends_at` carry over only if the submission's proto-session fields were set (`submissions.starts_at`/`ends_at` from the Add Abstract drawer), else both null (lands in the tray). **Done when:** promoting a seeded accepted submission creates exactly one session linked via `submission_id`, with the submission's title/description/track/format and all its participants copied as speakers; promoting the same submission twice is a no-op the second time.

6. **UI: `session-form-dialog.tsx`.** shadcn `Dialog`/`Sheet` with fields: Title (text), Description (`RichTextEditor` from M05b), Format/Track/Room (`Select`, options from vocab fixture/real), Day + Start/End time (`DateTimePicker` in event tz from M05b, or "Unscheduled" toggle that nulls both), Speakers (multi-select from `listContacts`-style fixture until portal/speakers data is easily queryable — accept a plain contact-id+name list prop for now), Status (draft/published switch). ## Guardrails
- **Event scoping (R4):** every exported function's first param is `eventId`; every query filters by it; composite FKs make a cross-event join a constraint violation, not just a bug — but still always pass `eventId` explicitly, never rely on the FK alone.
- **`moveSession` is one of exactly 8 audited runtime `withTx` functions** (resolution #4). Do not add a second `withTx` call anywhere in this module — `saveSession`'s publish-with-schedule-change path is deliberately non-atomic (documented in Step 3) and does not justify a ninth deployed transactional function.
- **Half-open interval math lives only in M29's `conflicts.ts`** — do not reimplement overlap checks here; call `detectConflicts`/`toScheduledSession`.
- **NULL-time sessions must never crash a view** (agenda-embeds.md edge case #3) — `getSchedulableSessions` filters them out structurally before they can reach conflict math or a grid layout; `listSessions`/List view/tray must render them with `<Dash>` for date/room/track cells, never `undefined.toLocaleString()`.
- **Timezone**: day-grouping and the day-switcher tabs use `eventDayKey`/`formatInZone` from `time.ts` — never `new Date(starts_at).getDate()` or any browser-local-time computation. A 9pm PT session must bin to the correct event-tz day even though its UTC date is the next day (edge case #2).
- **Speaker/room/track deletes SET NULL onto sessions** (already enforced by the FK's `ON DELETE SET NULL`) — no app code required to "handle" this, but confirm List/tray render a null track/room as `<Dash>` rather than crashing, since it will happen the moment M11's vocab CRUD ships a delete.
- **XSS**: `description_html` passes through `sanitize()` on every write in this module (create AND update) — never trust that the dialog's `RichTextEditor` output is already clean; the seed's `<img onerror>` probe on a session description must render inert everywhere this module displays it.
- **Sanitize the promote path too**: `description_html` copied from the submission during `promoteSubmission` is already-sanitized (submissions sanitize on their own write path per resolution #2) but re-run it through `sanitize()` anyway on insert — cheap, and removes any assumption about another feature's write discipline.
